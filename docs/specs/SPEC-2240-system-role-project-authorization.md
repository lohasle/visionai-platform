# SPEC-2240 统一复用系统角色管理与项目授权

状态：已完成
Linear：LOH-21

## 背景

项目中心原先在 `ai_project_member.roles` 中保存一套固定角色代码，同时系统管理又维护 `roles`、`user_roles`。双重角色来源会造成名称、启停状态、人员分配和实际 API 权限不一致。

## 目标

- `roles` 与 `user_roles` 是角色定义和用户角色分配的唯一来源。
- 项目中心只维护用户是否属于项目，不再创建、编辑或保存项目角色。
- 项目 API 同时校验租户、项目成员关系和用户当前启用的系统角色。
- 系统角色被停用或从用户移除后，项目权限立即失效。

## 系统角色

每个租户初始化以下 VisionAI 内置角色，名称、启停状态、菜单权限和用户分配均在“系统管理”中查看和维护：

| 角色标识 | 默认名称 |
| --- | --- |
| `PROJECT_OWNER` | 项目负责人 |
| `DATA_MANAGER` | 数据管理员 |
| `ANNOTATOR` | 标注员 |
| `REVIEWER` | 审核员 |
| `ALGORITHM_ENGINEER` | 算法工程师 |
| `APPROVER` | 模型审批人 |
| `OPS` | 平台运维 |
| `AUDITOR` | 审计员 |

内置角色的标识不可修改、角色不可删除，但可以重命名、停用并调整菜单和数据权限。项目记录中的 `owner_user_id` 仍代表项目所有权，不构成第二套角色定义。

## API 契约

- `PUT /ai-platform/projects/{projectId}/members` 只接受 `userId`。
- `GET /ai-platform/projects/{projectId}/members` 从系统用户和系统角色实时组装成员、账号状态与角色详情。
- 所有 `requireProjectRole` 检查均查询启用的系统角色，不再读取项目成员 JSON。
- 标注员和审核员候选人必须同时满足：同租户启用用户、项目成员、拥有对应启用系统角色。

## 兼容迁移

启动迁移读取旧 `ai_project_member.roles` 角色代码，将其转换为对应的 `user_roles` 关联，成功后清空旧 JSON。旧字段仅为数据库兼容保留，业务代码不得读取或写入角色。

## 验收

1. 项目成员弹窗只能选择系统用户，不显示项目角色编辑控件。
2. 项目成员列表展示系统角色名称；角色入口跳转到系统角色管理。
3. 通过系统用户管理分配 `REVIEWER` 后可执行审核；移除或停用后立即返回 403。
4. 旧成员角色在升级时自动迁移，现有项目仍可访问。
5. Go 单测、前端类型检查、生产构建和 COCO128 端到端脚本通过。

## 验收结果

- 系统角色共 8 个，旧项目成员角色已迁移为 `user_roles`。
- 审核用户移除 `REVIEWER` 后权限即时变为 403，恢复角色后重新可用。
- 浏览器确认项目中心只保留成员选择并展示系统角色名称。
- COCO128 新链路项目 #16：128 张图片、929 个标注、GPU 训练 #8 成功、评估 #11 通过、部署 #7 运行、反馈标注任务 #19 READY。
